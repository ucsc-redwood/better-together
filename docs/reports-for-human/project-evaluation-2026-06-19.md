## Executive summary

BetterTogether is a mature, unusually well-engineered research framework for profile-guided software pipelining across heterogeneous edge SoCs (OMP/CUDA/Vulkan). The recently-landed component-structure refactor is genuinely sound: a thin-root CMake orchestrator fans out to per-component subdirectories, the runtime is provably app-agnostic (enforced by a CTest guard, not just convention), and the three backends are unified behind one well-chosen seam (std::pmr::memory_resource + a compiler-checked AppTraits/Runner contract). The optimizer/profiling pipeline is correct where it counts — the load-bearing stage->PU assignment — and recently fixed two real z3 modeling bugs with regression tests, backed by a schema-validated fail-loud JSONL store. Documentation, onboarding, build portability, and a newly-added hosted CI + branch-protection model are all above-average for a research codebase; the everyday OMP gate is reproducibly green and the project is honest about its biggest known landmines.

The cross-cutting risk, confirmed independently across four of six dimensions, is that "green" provides almost no signal on the backends that matter most. The hosted CI runs OMP only; the CUDA/Vulkan/Android fleet matrix is entirely manual; the per-cell coverage checker that exists precisely to catch "skip-exit-0 looks like a pass" is wired into nothing; the named dev->main promotion gate (`just test`) silently swallows fleet test failures through a `| grep | tail` pipe and cannot go red; and main branch protection requires 0 reviews. Today the fleet checker reports COVERAGE RED — 6 of 12 GPU cells (both phones' Vulkan, the unique subgroup-16 Mali paths) have never run — and nothing surfaces this automatically. So the "main is verified on all backends" guarantee currently rests on an unautomated, failure-masking manual step. The other notable structural debt is the team-acknowledged SafeAppData defect (a test oracle fused into the production tree data type, dragging an OMP-pipeline singleton into every backend's startup), plus a cluster of stale post-refactor docs (the removed octree app still documented as a live 4th app in six places; the headline CSV-vs-JSONL data-flow diagram contradicts the code) that would actively mislead a new external researcher. None of these corrupt correctness of the framework's actual output, which keeps the project solidly in good shape — but the verification/gating gap is the thing to fix before leaning on "main" as a citable, trustworthy artifact.

## Top strengths

- Runtime is provably app-agnostic by mechanism, not convention: scripts/guard_runtime_agnostic.py strips comments, derives the forbidden app-namespace/include list from vocab.json (single source of truth), is wired as a CTest on the omp gate, and passes — independently confirmed.
- Backends are unified behind one well-chosen seam: every backend's AppData is allocated from a std::pmr::memory_resource (CudaPinnedResource / VulkanMemoryResource / new_delete_resource), so the same pipeline_runner harness drives OMP, CUDA zero-copy-pinned, and Vulkan VMA unchanged; AppTraits<Dispatcher> turns contract violations into named compiler diagnostics.
- Build/portability is reproducible and verified empirically: CPM deps pinned by exact tag + SHA, a fresh configure resolves 100% offline from cache, the three committed generated files byte-match a fresh regeneration, and a real bt_core build leaves the tree git-clean (codegen idempotency holds).
- Differential testing avoids the self-comparison tautology where it matters: cifar checks all three backends against an independent double-precision reference, and tree anchors its shared OMP golden with libmorton, Karras invariants, an O(n^2) brute force, and a hand-built tiny-octree — plus deliberate vacuous-pass guards (ASSERT_GT, non-empty-CSR).
- The optimizer fixed two genuine z3 modeling bugs (degenerate gap-only objective; absent-tier selection) with end-to-end solver regression tests, and the profiler->optimizer contract is schema-validated and fail-loud (rejects invalid records, refuses to fabricate zero-cost stages); the load-bearing stage->PU assignment is trustworthy.
- Documentation is layered and verifiable, not aspirational: the documented OMP gate runs clean as promised, hardware docs capture real fleet gotchas (fish shells, adb stdin, eIntegratedGpu, CUDA-13 CUB breakage), and the biggest model landmine (AlexNetCIFAR-11 vs implemented SmallAlexNet-9) is disclosed consistently across README/CLAUDE.md/docs/vocab.json.

## Top risks

- **[high]** The backends that define the project's thesis (CUDA/Vulkan) have zero automated gating, and fleet coverage is currently RED — the most divergent GPU paths are unverified and nothing flags it.  
  _evidence:_ scripts/check_fleet_coverage.py reports '6 expected cell(s) not RAN' and exits non-zero — both phones' Vulkan (the unique subgroup-16 Mali paths) for tree/cifar-dense/cifar-sparse have never run (reproduced); .github/workflows/ci.yml runs only fmt-check + ctest -L omp -E pipeline-e2e + optimizer pytest, with no step invoking the checker.
- **[high]** The named dev->main promotion gate cannot programmatically fail, so the 'main verified on all backends' guarantee rests on an unautomated, failure-masking manual step.  
  _evidence:_ justfile:74 and justfile:92 run each fleet binary as `... 2>&1 | grep -E 'tests ran|PASSED|FAILED|SKIPPED' | tail -8`; the pipe discards the binary exit code and the remote script lacks pipefail/-e, so a failing test still exits 0; main branch protection has required_approving_review_count=0 and enforce_admins=false (confirmed via GitHub API).
- **[medium]** A test oracle is fused into the production tree data type, dragging an OMP-pipeline singleton and double the buffers into every backend's deployed startup path (team-acknowledged as finding #29).  
  _evidence:_ All production tree dispatchers operate on tree::SafeAppData (apps/tree/omp/dispatchers.hpp:8-16), whose ctor copies const golden buffers from HostTreeManager::getInstance() and whose initialize() runs the full OMP reference pipeline (safe_tree_appdata.cpp); verification adds that its count setters are no-op stubs — a latent correctness hazard masked by the precomputed golden. (Verification refuted the eval's 'roles inverted' sub-claim: tree::AppData is itself oracle infrastructure, not a clean prod type displaced into tests.)
- **[medium]** Reported optimizer metrics are partly unreliable and baselines can be inflated, risking misleading speedup/gapness numbers in published results even though the assignment itself is correct.  
  _evidence:_ solver.py:87 overwrites the chunk-derived gapness with z3's loosely-constrained T_max - T_min, so a schedule's stored gapness=0.737 contradicts its own UID-derived gap of 0.02 in tmax mode (reproduced); single-sample 'abandoned' cells (cv trivially 0.0) bypass the CV gate (profiling_loader.py:90-93) and flow into baseline column sums, inflating reported speedups.
- **[medium]** Stale post-refactor documentation would actively mislead a new external researcher about what apps exist and how the core data flow works.  
  _evidence:_ The removed octree app is still documented as a live 4th app in six places including 03-unit-testing.md:11,44,69 (which tells contributors to run tests that cannot exist); CLAUDE.md:7 and 00-project-goal.md:22 say 'BT-Profiler -> CSV -> BT-Optimizer' while README, doc 06, and the code (profiling_loader.py:2) agree the optimizer reads a JSONL store with 'no CSV step'.
- **[medium]** The concurrent-runtime correctness surface (SPSC ring, worker loop, pool reuse, cross-tier visibility, GPU command-buffer reuse) has no hosted-CI gate because thread-pinning hard-aborts on small machines, and the GPU pipeline-e2e check is weaker than the OMP one.  
  _evidence:_ affinity.hpp:99 throws on sched_setaffinity failure with no fallback; devices/pc.json declares 24 cores, so hosted ~4-core runners abort, forcing ci.yml to exclude pipeline-e2e entirely; both CUDA and Vulkan pipeline-e2e CheckItem assert only CheckStage7 while OMP asserts interior CheckStage4/CheckStage6 (test_pipeline_main.cpp:73-89 vs the GPU variants).

- **P2** (L) — Resolve the SafeAppData test-oracle fusion (review #29): make production tree dispatchers operate on a clean mutable AppData and compose a separate GoldenOracle for the differential test, converging tree onto the cleaner cifar recompute-the-reference pattern; also fix the no-op count setters.  
  _why:_ Largest structural smell — deletes test-only allocations and a global-OMP-singleton from the deployed path and removes a latent correctness hazard — but it is invasive and the team already tracks it; schedule rather than rush.

Then hoist the interior CheckStage4/CheckStage6 assertions into the shared GPU pipeline-e2e CheckItem.  
  _why:_ Restores an automated gate for the concurrent-runtime surface (where the project has already found real visibility/race bugs) and equalizes the GPU vs OMP check depth.
- **P3** (M) — Close the remaining build/test seams: add a tiny hardware-free CTest asserting the baked h/*_spv.h set matches all_shaders.hpp's active includes (and prune the orphaned octree_*/tmp_single_radixsort_* shaders); add a committed JSONL fixture + pytest-collected test for baselines.py tier selection; reconcile the two z3 lockfile pins (4.16 in optimizer vs 4.15.1 at root) given the SMT-sensitive contract tests run on the 4.16 lock in CI; reconcile the Python version floors and default CUDA to OFF without a preset.  
  _why:_ Each is individually low-severity, but together they remove silent-drift seams and footguns that will eventually bite; cheap hardening for a long-lived research codebase.

## Per-dimension detail

### Architecture & code structure — 4/5

The component split (platform/ apps/ runtime/ profiler/ tools/) is genuinely sound and well-reasoned. The root CMakeLists is a thin orchestrator with one add_subdirectory per component; each app owns its sources and contributes them to shared backend libs via target_sources(); the runtime is provably app-agnostic (a comment-stripping CTest guard, not just convention, enforces it and currently passes); and the three backends are unified behind a single clean seam — std::pmr::memory_resource (CUDA CudaPinnedResource / Vulkan VulkanMemoryResource / OMP new_delete_resource) plus a per-app Runner concept and the AppTraits compiler-checked contract. Separation of concerns across the BT-Profiler -> CSV/JSON -> BT-Optimizer -> schedule -> BT-Implementer file boundary is clear. What holds the score back from 5 is one significant architectural defect that the team already knows about (the tree::SafeAppData test-oracle fused into the production data type, dragging a process-global singleton that runs the OMP reference pipeline into every backend's startup path), an inconsistent AppData design between tree and cifar, the deliberate-but-real backend-lib bundling that defeats fine-grained decoupling, orphaned shaders left in the registry after the octree app removal, and a stale build-file comment. None of these are blocking; the structure is maintainable and the boundaries are mostly in the right places.

**Strengths:**
- Runtime is provably app-agnostic, not just by convention: scripts/guard_runtime_agnostic.py strips comments then forbids any app namespace / apps/ include in runtime/, derives the forbidden list from vocab.json (single source of truth, auto-covers a 4th app), is wired as a CTest on the omp gate, and passes (verified: 'guard-runtime-agnostic OK'). runtime/ includes only platform/ and runtime/ headers (verified via grep).
- Backend abstraction is unified behind one well-chosen seam: every backend's AppData is allocated from a std::pmr::memory_resource, so the same pipeline_runner.hpp / make_dataset harness drives OMP, CUDA (zero-copy pinned UMA) and Vulkan (VMA) unchanged. platform/mem/mr_ptr.hpp::as_mr_ptr cleanly papers over the one signature difference (CUDA returns get_mr() by ref, Vulkan by pointer) without touching ~40 call sites.
- AppTraits<Dispatcher> (runtime/app_traits.hpp) replaced a fragile pre-include magic-typedef ODR contract with a real C++20 concept (BtRuntimeApp) that turns a missing/wrong cell field into a named compiler diagnostic; keyed on Dispatcher (correctly, since tree's OMP+CUDA share SafeAppData and cifar's 3 backends share one AppData, so AppData can't be the key).
- Thin-root CMake orchestration with genuine per-component ownership: root is options+deps+helpers only (CMakeLists.txt:175-181), shared bt_add_{omp,cuda,vk}_{run,app,test} helpers live in cmake/bt_targets.cmake, and each apps/<app>/CMakeLists.txt contributes its own kernels via target_sources — so a new app is self-contained and the profiler app list is set in one place (profiler/CMakeLists.txt:9, BT_PROFILED_APPS) to avoid foreach drift.
- Backends are orthogonal, combinable CMake options (hybrid = enable two), CUDA/Vulkan code is fully #if-guarded, and the schedule contract (runtime/schedule.hpp) encodes hard-won invariants as up-front guards with excellent diagnostics (validate_schedule_coverage, first_unavailable_pu, first_concurrent_gpu_chunk) rather than letting them fail deep in a worker thread.

**Findings:**
- **[high]** Test oracle fused into the production data type: tree::SafeAppData carries golden buffers and drags an OMP-pipeline singleton into every backend's startup _(verify: partially-confirmed)_  
  The type that ALL production tree dispatchers operate on (OMP/CUDA/Vulkan dispatchers take SafeAppData&, see apps/tree/omp/dispatchers.hpp:8-14) is apps/tree/safe_tree_appdata.hpp's SafeAppData, which interleaves const golden reference buffers (u_morton_keys_s1, ...) with the production _out buffers (u_morton_keys_s1_out, ...). Its constructor copies those goldens from HostTreeManager::getInstance() — a process-global singleton whose initialize() (safe_tree_appdata.cpp:17-60) runs the ENTIRE OMP reference pipeline (stages 1..7) on first use. Both production runners instantiate it: apps/tree/cuda/main.cu:20 'tree::SafeAppData appdata(&disp.get_mr())' and apps/tree/vulkan/run_main.cpp:9 'Task<tree::vulkan::VkAppData_Safe>'. So a deployed CUDA or Vulkan tree run computes the full CPU golden at startup and pays for ~double the buffers, purely to serve the differential test. Meanwhile the clean production type tree::AppData (tree_appdata.hpp) is now used ONLY by the test oracle (tree_diff_oracle.hpp, omp/test_main.cpp, testing/tree_ref.hpp) — the roles are inverted.  
  _evidence:_ apps/tree/safe_tree_appdata.hpp:13-105 (const golden + _out fields in one struct, getInstance() singleton); apps/tree/safe_tree_appdata.cpp:17-60 (initialize() runs OMP stages 1..7); apps/tree/omp/dispatchers.hpp:8-16 (prod dispatchers take SafeAppData&); apps/tree/cuda/main.cu:20 + apps/tree/vulkan/run_main.cpp:9 (prod runners use it); grep shows tree::AppData consumed only by test files  
  _fix:_ Split the oracle out of the core type: make production dispatchers operate on tree::AppData (mutable, no golden), and have the differential test wrap or compose AppData with a separate GoldenOracle holding the const reference buffers + the HostTreeManager-built data. This deletes the test-only allocations and the global-singleton-runs-OMP-at-startup from the deployed BT-Implementer path. This is tracked as code-review finding #29 / the SafeAppData debt; it is the single biggest structural smell and worth scheduling rather than leaving open-ended.
- **[medium]** Inconsistent AppData design between apps (tree dual AppData/SafeAppData vs cifar single AppData) _(verify: confirmed)_  
  tree uses the two-type AppData + SafeAppData scheme above, while cifar-dense/cifar-sparse use a single AppData (apps/cifar-dense/appdata.hpp:24) seeded in-constructor with the fixed 114514 seed and validated by recomputing an independent double-precision reference (cifar_dense_diff_oracle.hpp) rather than by carrying golden buffers in the type. The cifar design is cleaner and does not fuse the oracle into the type. The asymmetry means a contributor adding a 4th app has no single canonical pattern to follow, and the runtime's AppTraits already has to special-case the keying (app_traits.hpp:8-13) because the two apps model AppData so differently.  
  _evidence:_ apps/cifar-dense/appdata.hpp:24-91 (single self-seeding AppData, recompute-reference oracle) vs apps/tree/safe_tree_appdata.hpp:13 (golden-carrying SafeAppData); runtime/app_traits.hpp:8-13 documents the divergence  
  _fix:_ Converge tree onto the cifar pattern (recompute-the-reference oracle, single mutable AppData) as part of resolving the SafeAppData debt, so 'how an app models its data + how it is differentially tested' is one documented convention, not two.
- **[low]** Orphaned Vulkan shaders left in the compiled registry after the octree mini-app removal _(verify: confirmed)_  
  The octree mini-app was removed (commit fbf084f) but its four compute shaders remain compiled into the shader registry: octree_morton, octree_build_radix_tree, octree_edge_count, octree_build_octree_nodes are #included and SHADER_ENTRY-registered in all_shaders.hpp but no dispatcher requests them (grep for make_algo of those names returns nothing; only tree_*, multi_radixsort_*, new_cifar_* are used). The three tmp_single_radixsort_warp{16,32,64} shaders are likewise registered but unused (the live path uses multi_radixsort_*). These are dead weight baked into every Vulkan binary's shader table and obscure which shaders are actually live.  
  _evidence:_ platform/engine/vulkan/shaders/all_shaders.hpp:36-38 (tmp_single_radixsort) and :57-60,125-127 (octree_*) registered; grep 'make_algo("octree_|make_algo("tmp_single' across apps/platform/profiler/tools returns no hits; git fbf084f 'remove orphaned octree mini-app'  
  _fix:_ Drop the octree_* and tmp_single_radixsort_* .comp/.spv/_spv.h files and their all_shaders.hpp entries (recover from git history if octree returns). Per CLAUDE.md these are orphans the octree-removal change should have swept; flagging rather than deleting since this is a read-only review.
- **[low]** Stale build-file comment claims removed sources still exist under utility/ _(verify: confirmed)_  
  The root CMakeLists header comment states the unported volk diagnostics and NNAPI/EdgeTPU targets 'still live under utility/ and can be re-added when needed' (CMakeLists.txt:5-6), but utility/ does not exist (ls fails) — it was folded away in the P5a split (commit 9a0cb2f) and the dead code removed 2026-06-18 (CLAUDE.md). A reader trusting the comment would go looking for a directory that is gone; the accurate pointer is git history.  
  _evidence:_ CMakeLists.txt:4-6 ('their sources still live under utility/'); `ls -d utility/` -> 'No such file or directory'; CLAUDE.md notes volk/NNAPI removed as dead code 2026-06-18 (recover from git history)  
  _fix:_ Update the comment to say the volk/NNAPI sources were removed and live only in git history (matching the CLAUDE.md wording), so the build file's self-documentation stays truthful.
- **[low]** Backend libraries are bundled, so every executable links all apps' kernels (deliberate, but a real coupling cost) _(verify: confirmed)_  
  bt_cuda is a single static lib (platform/CMakeLists.txt:59) and every app's CUDA kernels are added to it (apps/cifar-dense/CMakeLists.txt:5, apps/cifar-sparse:5, apps/tree:9-22). Consequently run-tree-cu links bt::cuda which also contains the cifar kernels (and vice versa); the root CMake comment acknowledges this ('every target links the whole bt::core/cuda/vulkan', CMakeLists.txt:16-18) and chose the runtime guard over per-target link scoping. The upside is simplicity; the downside is that app-to-app decoupling is enforced only socially/by the namespace guard (which covers runtime/ only, not app-to-app), build times and binary sizes don't scale down per app, and a compile error in one app's kernels breaks every binary on that backend.  
  _evidence:_ platform/CMakeLists.txt:59 (single add_library bt_cuda) + apps/*/CMakeLists.txt target_sources(bt_cuda ...) for all three apps; CMakeLists.txt:16-18 documents the bundling tradeoff; guard_runtime_agnostic.py scopes RUNTIME only  
  _fix:_ Acceptable for a 3-app research codebase; revisit if app count grows. A per-app OBJECT library per backend (bt_cuda_tree, bt_cuda_cifar_dense) linked selectively would restore per-app isolation and incremental-build scaling without changing the public bt::cuda interface. Document explicitly that app-to-app source isolation is NOT build-enforced today.

- The summary/strengths assert 'tree's OMP+CUDA share SafeAppData and cifar's 3 backends share one AppData, so AppData can't be the key' as justification for Dispatcher-keying -- I confirmed this independently (8 AppTraits<...Dispatcher> specializations found; cifar-dense OMP/CUDA/Vulkan all key off cifar_dense::AppData; tree OMP+CUDA both use SafeAppData). The strength is accurate; worth noting it checks out since it underpins the medium finding.
- All backend memory_resource strengths verify cleanly and could have been cited more concretely: CudaPinnedResource is at platform/engine/cuda/cu_mem_resource.cuh:20 ('final : public std::pmr::memory_resource'), VulkanMemoryResource at platform/engine/vulkan/vma_pmr.hpp:30, and pipeline_runner.hpp:179 constrains on 'requires BtRuntimeApp<Dispatcher>'. The eval's mr_ptr.hpp claim is confirmed verbatim (the header's own comment says ~40 call sites).
- A structural smell the eval did not flag: SafeAppData's getters/setters are no-op stubs -- set_n_unique/set_n_brt_nodes/set_n_octree_nodes (safe_tree_appdata.hpp:102-104) take '[[maybe_unused]]' args and do nothing, because the counts are const members fixed at construction from the singleton. - The eval did not note that the BT-Profiler->CSV->BT-Optimizer->schedule->BT-Implementer 'separation of concerns' claim in the summary was not independently substantiated with file evidence in any strength/finding (I did not deep-verify it either; the profiler app list BT_PROFILED_APPS at profiler/CMakeLists.txt:8 is confirmed, but the cross-tool file-boundary clarity is asserted, not evidenced).

A score of 4 is still defensible, but the headline finding's accuracy should be downgraded to partially-confirmed.

### Build system & portability — 4/5

A mature, coherent CMake-only build system. The root CMakeLists is a thin orchestrator that fans out to one add_subdirectory per component (platform/apps/runtime/profiler/tools), with shared target helpers (cmake/bt_targets.cmake), a generic codegen helper (bt_codegen.cmake), an opt-in shader-bake (bt_shaders.cmake), and pinned CPM dependency management. Five presets (pc/jetson/vulkan/android/android32) map cleanly onto the documented build matrix, backends are orthogonal combinable options, and cross-compilation is handled by a reproducible Docker image plus three well-commented toolchain files with sensible NDK/CUDA resolution-order fallbacks. I empirically verified the most load-bearing portability property — committed-fallback codegen consistency: the three generated files (device_specs_embedded.hpp, bt_vocab.hpp, bt_vocab.py) byte-match what their scripts emit, all 29 shader comp/spv/h triples are consistent and fully referenced with zero orphans, a fresh pc configure resolves entirely from the CPM cache (offline-capable), and a real bt_core build left the source tree git-clean (codegen idempotency holds). Deductions are for a handful of stale post-refactor path references in the codegen contract, a hand-curated all_shaders.hpp that the bake does not regenerate (a silent-drift seam), and minor DRY/version-floor nits — none block builds, but they are real maintainability/portability hazards.

### Testing strategy & coverage — 4/5

The testing strategy is well-designed and genuinely strong for a research codebase. The OMP-as-oracle, in-process differential approach (fixed seed 114514, exact for integer/structural stages, NearEqual for floats) is sound and sidesteps x86-vs-aarch64 FP drift with no shipped goldens. Crucially, the design avoids the obvious "OMP-self-comparison tautology" trap: cifar tests compare every backend against an INDEPENDENT double-precision reference (platform/util/testing/cnn_ref.hpp), and tree backs its shared OMP golden with independent anchor tests (libmorton, Karras invariants, an O(n^2) brute-force, and a hand-built tiny-octree ground truth) plus order-independent structural oracles for non-deterministic GPU scatter stages. The everyday gate (ctest -L omp) is reproducibly green locally (9/9 passed, verified) and deterministic across reruns; the optimizer has real z3 regression tests (14 passed). The biggest trustworthiness gap: "green" on the everyday CI gate gives ZERO signal on the CUDA/Vulkan backends (they GTEST_SKIP and skip-exit-0 off-fleet), and the fleet-coverage manifest checker currently reports COVERAGE RED — 6 of 12 expected GPU cells (both phones' Vulkan: pixel + samsung) have never been marked RAN. Secondary issues: thread-pinning hard-aborts on small machines (forcing pipeline-e2e to be excluded from CI entirely), GPU pipeline-e2e CheckItem skips interior-stage checks that the OMP variant performs, and inconsistent seed semantics (tree static vs cifar fresh).

**Strengths:**
- Differential oracle avoids the self-comparison tautology where it matters most: cifar's cnn_ref.hpp is an independent double-precision reimplementation (Conv2dRef/MaxPool2dRef/LinearRef) so OMP, CUDA, and Vulkan are ALL checked against external ground truth, not against each other (platform/util/testing/cnn_ref.hpp:1-13, cifar_dense_diff_oracle.hpp:6-9)
- Tree's shared OMP golden is anchored by genuinely independent ground truth in the OMP binary: libmorton reference, Karras radix-tree invariants, an O(n^2) brute-force prefix_n/split check, and a decisive hand-built tiny-octree comparison (apps/tree/omp/test_main.cpp:63-510) — without these the GPU-vs-golden compare would be circular
- Sophisticated handling of legitimately non-deterministic GPU output: stage-7 octree compares an order-independent geometric edge SET and separates internal topology (must match) from last-writer-wins contended leaf slots (tolerated), instead of failing on benign scatter-order differences (tree_diff_oracle.hpp:104-256)
- Vacuous-pass guards are deliberately planted: ASSERT_GT on n_unique/n_brt/n_octree before a prefix compare (tree_diff_oracle.hpp:70,79,93), and a shipped-CSR-non-empty guard that catches the historic all-zeros sparse regression that would otherwise pass against a zero reference (cifar-sparse/omp/test_main.cpp ShippedCsrIndicesAreNonEmpty)
- A machine-checked fleet-coverage manifest (fleet-coverage.json + scripts/check_fleet_coverage.py) explicitly closes the 'skip-exit-0 looks like a pass' hole by requiring each GPU cell to most-recently emit a 'BT-CELL ... RAN' marker — and it correctly exits 1 when cells are MISSING (verified)
- Hardware gating is non-fatal and correct: parse_args_test never exit()s on an unknown/missing device, backends GTEST_SKIP when their device is absent, and the device->subgroup-size map is data-driven from devices/*.json rather than a hardcoded allow-list (device_registry.cpp:7-16,42-76)

### CI/CD & dev workflow — 4/5

For a research-grade multi-hardware project, the newly-landed CI/dev workflow is unusually mature and well-reasoned. A 3-job hosted gate (.github/workflows/ci.yml: format / build+ctest-L-omp / optimizer pytest) is live, green on `dev` (gh run 27843166518, ~2-3 min), and enforced as required status checks via real branch protection on both `dev` and `main` (confirmed via the GitHub API). The formatting toolchain is broad (clang-format/ruff/gersemi/shfmt/prettier) and genuinely reproducible — pip formatters are version-locked in uv.lock (clang-format 22.1.5, ruff 0.15.18, gersemi 0.27.7), shfmt/prettier are pinned by tag/version, generated code is deliberately excluded, and a .git-blame-ignore-revs keeps the bulk reformat out of blame. The two-branch dev->main promotion model is documented (CONTRIBUTING.md) and the honest scoping decision — keep CUDA/Vulkan/Android off the hosted gate because hosted runners lack the GPUs and a >=9-core topology — is correct and well-commented in the YAML. The gaps are real but largely acknowledged: the fleet hardware-in-the-loop matrix is entirely manual (`just test`), the per-cell coverage checker (scripts/check_fleet_coverage.py) is not wired into any automated gate, the `just test` promotion gate silently swallows test failures through a `| grep | tail` pipe, `main` requires 0 approving reviews, and there is no CD/release automation at all. Solid foundation, but the "main is verified" guarantee currently rests on an unautomated, failure-masking manual step.

**Strengths:**
- Branch protection is actually configured, not just documented: GitHub API confirms main has strict required status checks (all 3 CI jobs), required_linear_history=true, allow_force_pushes=false, allow_deletions=false; dev requires the same 3 checks. This matches CONTRIBUTING.md's claim that main only moves by PR promotion.
- Formatter reproducibility is taken seriously: clang-format/ruff/gersemi are exact-pinned in uv.lock (22.1.5 / 0.15.18 / 0.27.7), shfmt pinned to v3.13.1 by URL, prettier pinned to 3.8.4 via bunx — and the justfile comment explicitly calls out clang-format output drift as the reason. fmt and fmt-check share one source of truth.
- Honest, well-documented scoping of what CAN'T run on hosted runners: ci.yml lines 57-66 exclude pipeline-e2e because hosted runners have ~4 cores vs the 'pc' profile's 24-core pinning, and the top-of-file comment explains CUDA/Vulkan/Android are fleet-only. This avoids a flaky/false-green gate.
- Good GitHub Actions hygiene: concurrency group with cancel-in-progress (ci.yml:14-16), CPM dependency caching keyed on cmake/CMakeLists hashes (ci.yml:47-52), uv cache enabled. The OMP build+test completes in ~2m46s.
- fmt-check excludes generated code (*/generated/*, *_spv.h, .comp GLSL, optimizer/smt/bt_vocab.py via pyproject) so codegen re-emission doesn't make the gate non-deterministic — a subtle correctness detail handled correctly.
- The optimizer pytest job covers load-bearing logic (test_schedule_contract, test_baselines, test_minimize_mode, test_case, test_vocab), not just smoke tests, giving the Python half of the toolchain real coverage.

**Findings:**
- **[high]** The named dev->main promotion gate (`just test`) silently swallows fleet test failures  
  CONTRIBUTING.md:36-38 makes `just test` the gate that promotes dev to main ('the full fleet matrix'). But the _test-ssh and test-samsung recipes run each binary as `./$b --device ... 2>&1 | grep -E 'tests ran|PASSED|FAILED|SKIPPED' | tail -8`. The pipe discards the test binary's exit code (the pipeline status is grep/tail's), and although the recipe greps FOR the word FAILED it never tests whether FAILED appeared. A failing test prints 'FAILED', it is tailed to the console, and the recipe still exits 0. Under `set -euo pipefail`, pipefail only catches grep returning non-zero (no match) — the opposite of a failure. So the human-facing promotion gate cannot programmatically fail. Notably the standalone scripts/run-on-rocky.sh:55 (`exit $fail`) and run-on-android.sh DO aggregate failures correctly — the regression is specifically in the justfile recipes the docs point maintainers at.  
  _evidence:_ justfile:74 and justfile:92 (`| grep -E ... | tail -8`); CONTRIBUTING.md:36-38 names `just test` as the promotion gate; contrast scripts/run-on-rocky.sh:47-55 which does `set -e; ...; exit $fail`  
  _fix:_ Make the fleet recipes fail loud: capture each binary's exit status (e.g. run the binary, save $?, then grep a saved log) and `exit 1` if any cell fails; or have `just test` invoke the run-on-*.sh scripts (which already track failures and emit BT-CELL markers) and then run scripts/check_fleet_coverage.py as the final assertion. The gate that guards the public branch must be able to go red.
- **[high]** Fleet hardware-in-the-loop is entirely manual and unwired — main's 'verified on all backends' claim is unenforced  
  CONTRIBUTING.md:9 states every change on main has passed the real-hardware fleet (CUDA/Jetson, Vulkan/Rocky, Android). But nothing automates or records this. There is exactly one workflow (ci.yml) and it explicitly runs only OMP. scripts/check_fleet_coverage.py exists precisely to detect never-run GPU cells (a clever guard against GTEST_SKIP-as-pass), and run-on-*.sh emit BT-CELL markers for it — yet a grep of .github/ and justfile shows check_fleet_coverage/fleet-coverage is referenced nowhere as an executed step. So the fleet result is a human assertion with a checker that no gate invokes. CONTRIBUTING.md:31 and ci.yml:6 both admit a scheduled self-hosted job is 'once wired'/TODO. For a project whose entire thesis is heterogeneous multi-backend correctness, the backends that matter most have zero automated gating.  
  _evidence:_ `ls .github/workflows/` = ci.yml only; `grep -rn 'check_fleet_coverage|fleet-coverage' .github/ justfile` returns nothing executable; CONTRIBUTING.md:9 ('passed ... the real-hardware fleet') vs CONTRIBUTING.md:31 ('once wired, a scheduled self-hosted CI job'); scripts/check_fleet_coverage.py docstring  
  _fix:_ Add a self-hosted-runner workflow (or a scheduled cron job) that runs `just test` on the fleet and ends with scripts/check_fleet_coverage.py against a freshly-regenerated fleet-coverage.log, committing/uploading the log as the artifact of record. Until then, soften CONTRIBUTING.md to say fleet verification is a manual maintainer step, so the 'verified' guarantee isn't overstated to external researchers.
- **[medium]** main branch protection requires 0 approving reviews — self-merge to the 'public verified' branch is allowed  
  main's protection has required_approving_review_count=0 (with dismiss_stale_reviews=true, which is moot with 0 required) and enforce_admins=false. CONTRIBUTING.md:12 promises 'main only ever moves by promotion from dev (via pull request) — never a direct push', and a PR is indeed required, but a single maintainer can open and immediately merge their own dev->main PR with no second pair of eyes and (per finding above) no automated fleet gate. The status-check requirement helps, but the OMP-only checks can be green while a CUDA/Vulkan regression sits unverified. For the branch external researchers are told to clone and cite, this is weaker than the prose implies.  
  _evidence:_ gh api repos/:owner/:repo/branches/main/protection -> required_pull_request_reviews.required_approving_review_count=0, enforce_admins.enabled=false; CONTRIBUTING.md:9,12  
  _fix:_ Set required_approving_review_count>=1 on main (and consider enforce_admins=true) so promotion to the citable branch needs at least one review, and gate it on the fleet check from the previous finding rather than only the OMP subset.
- **[medium]** optimizer pytest job uses a different, unpinned dependency resolution than the format job  
  The format job runs `uv sync --group dev` from the root uv.lock (exact pins). The optimizer job (ci.yml:79) runs `uv sync --extra test` inside optimizer/ against optimizer/uv.lock, and has no actions/cache step (unlike test-omp's CPM cache and format's uv cache), so it re-resolves/re-downloads every run. More importantly, the z3 solver — whose version can change SMT model selection and thus schedule-contract test outcomes — resolves to z3-solver 4.16.0.0 in optimizer/uv.lock but the project's stated z3 is 4.15.1.0 (root pyproject.toml:12). Two lockfiles for one repo invites drift between what CI tests and what a contributor running the root env gets, and an unpinned/uncached optimizer job is a latent flakiness/slowness source.  
  _evidence:_ ci.yml:76-80 (working-directory optimizer, `uv sync --extra test`, no cache); optimizer/uv.lock z3-solver=4.16.0.0 vs root pyproject.toml:12 z3-solver>=4.15.1.0; format job ci.yml:35-36 uses root `uv sync --group dev`  
  _fix:_ Add an actions/cache (or setup-uv enable-cache, as the other jobs do) to the optimizer job, and reconcile the two z3 pins — ideally a single workspace/lockfile, or at least document why the optimizer pins 4.16 while the root pins 4.15 and assert the schedule-contract tests are stable across that gap.
- **[low]** No CD / release automation; tagging and artifact publishing are absent  
  There is no release/publish workflow — `ls .github/workflows/` shows only ci.yml. `gh release list` is empty and there is a single git tag (iiswc2025-submission). For a paper-artifact project this is arguably acceptable, but CONTRIBUTING.md:9 frames main as the thing 'external researchers should clone, build, and cite' with no tagged, reproducible release point, no archived build artifacts, and no DOI/Zenodo hook. There is also no dependency/security automation beyond GitHub's auto Dependency Graph runs.  
  _evidence:_ `ls .github/workflows/` = ci.yml; `gh release list` empty; `git tag` = iiswc2025-submission only; CONTRIBUTING.md:9 ('clone, build, and cite')  
  _fix:_ Add a lightweight release workflow on tag push (cut a versioned tag per paper/milestone, attach the schema-validated devices/ + a build manifest, optionally a Zenodo archive) so 'cite this' maps to an immutable artifact rather than a moving main HEAD.
- **[low]** CI has no per-job timeout and all actions emit Node 20 deprecation warnings  
  ci.yml defines no timeout-minutes on any job (`grep timeout` -> NONE), so a hung build/test (e.g. a CPM fetch stall or a z3 non-termination) would burn the full GitHub default (~6h) before being killed. Additionally every run annotates that actions/checkout@v4, astral-sh/setup-uv@v5, actions/cache@v4, extractions/setup-just@v2 target Node 20, which GitHub is deprecating (forced onto Node 24). Both are minor maintenance issues but cheap to fix and will start failing/warning louder over time.  
  _evidence:_ `grep -n timeout .github/workflows/ci.yml` -> NONE; gh run view 27843166518 ANNOTATIONS: 'Node.js 20 is deprecated ... actions/checkout@v4, setup-uv@v5, setup-just@v2, actions/cache@v4'  
  _fix:_ Add `timeout-minutes:` to each job (e.g. 30 for build+test, 10 for format/optimizer) and bump the actions to their Node-24 major versions (checkout@v5, setup-uv@v6, cache@v4 latest, setup-just current) when available.

### Optimizer & profiling pipeline — 4/5

The optimizer/profiling pipeline is well-engineered and noticeably more correct than its history suggests: the recent code-review cycle fixed two genuine z3 modeling bugs (degenerate gap-only objective; absent-tier selection) and replaced a fragile regex-scrape→CSV path with a schema-validated, fail-loud JSONL store. The data flow is clean and verifiable end-to-end — I ran 02_gen_schedule_merged.py on real minipc/tree data and it produced schema-valid, plausibly-ranked schedules in 0.26s; all 14 pytest cases pass. Architecture is tidy (Case as the single path source of truth, vocab.json codegen keeping Python/schema/C++ in lockstep, a real cross-tool round-trip contract test). The main weaknesses are around the metrics layer and numerical confidence: the solver overwrites the chunk-derived `gapness` metric with z3's loosely-constrained `T_max - T_min`, so the stored `gapness`/`min_time` disagree with the UID and are unreliable in tmax mode; under-sampled "abandoned" cells (count=1, cv=0) slip through the CV noise gate and inflate baselines/speedups; and there is some doc/packaging drift (stale smt/README API, a matplotlib import that hard-couples the parse script to the optional plot extra). None of these corrupt the actual stage→PU assignment (the load-bearing output), which is why the score stays high.

**Strengths:**
- Two real z3 modeling bugs are fixed with regression tests: gapness-only was degenerate (a slow single-PU chunk has gap=0 and beat any pipeline), now T_max is the primary objective with gap as a lexicographic tie-breaker (constraints.py:82-93); absent CPU tiers are structurally forbidden via add_availability_constraints rather than only cost-penalized (constraints.py:27-39, solver.py:55). test_minimize_mode.py pins both.
- The profiling contract is schema-validated and fails loud, not silent: profiling_loader.validate() rejects schema-invalid records, drops throttled/high-CV samples, and raises on a fully-filtered or <min_runs cell (profiling_loader.py:52-102); data_loader refuses to fabricate a zero-cost stage if the requested GPU backend is missing (data_loader.py:51-56).
- Genuine cross-tool round-trip safety: dump_solutions_as_json validates every produced schedule against schemas/schedule.schema.json before writing (solution_analyzer.py:262), and test_schedule_contract.py checks both the committed fixture and a live solver run (incl. the GPU-hardware injection) against the same schema the C++ consumer reads.
- Path layout has one owner: orchestrate/case.py centralizes the device/app/backend directory schema and the short/long backend naming, eliminating the documented 02-vs-03 divergence; tested in test_case.py.
- Baselines are derived from the same measured store the solver uses (sum of backend column for GPU, fastest fully-measured CPU tier for OMP), keeping predictions in lock-step with the data and fixing the retired CSV path's N-run inflation bug (baselines.py:1-14, 47-67).
- Provenance and reproducibility are first-class: every JSONL record carries git_sha, timestamp, host, freq governor/locked, warmup, harness id (bm_prof_common.hpp:180-226); the calibrated time-budget sampler self-limits slow cells and records a real (large) measurement rather than a sentinel (bm_prof_common.hpp:82-115).
- Vocabulary is codegen'd from vocab.json (bt_vocab.py) and test_vocab.py asserts CPU_TIERS/CORE_TYPES/APP_STAGES and the schema core_type enum all agree, so the cost-matrix column order can't silently drift from the schedule schema.

**Findings:**
- **[medium]** Stored `gapness`/`min_time` metric disagrees with the UID and is unreliable in tmax mode (loose T_min) _(verify: confirmed)_  
  get_detailed_solution computes metrics['gapness'] = max-min over the ACTUAL chunk times and derives the schedule UID from it (solution_analyzer.py:178-190, 214-216). solver.py then OVERWRITES metrics['gapness'] (and min_time) with z3's Gapness = T_max - T_min (solver.py:78,87). z3's T_min is only constrained 0 < T_min <= every maximal-segment sum and is never optimized in max_time mode, so it floats. On real data (minipc/tree/vk, solution SCH-G3B4-G002) the chunks are GPU=1.237ms and Big=1.216ms (true gap 0.021 -> UID 'G002'), but the stored metric reports gapness=0.737, min_time=0.5 — a value matching neither chunk. So the UID says 0.02 while the JSON metric says 0.74 for the same schedule, and downstream consumers reading metrics.min_time/gapness in tmax mode get a meaningless free variable.  
  _evidence:_ solver.py:78,87 (overwrites metrics with z3 T_min/Gapness); solution_analyzer.py:190,214 (UID uses chunk-based gapness); observed in /tmp/bt_eval_sched/minipc/tree/vk/schedules_isolated_tmax.json: SCH-G3B4-G002 has metrics gapness=0.737,min_time=0.5 but chunks 1.237/1.216  
  _fix:_ Either drop T_min/Gapness from the reported metrics in max_time mode (they are unconstrained there), or compute min_time/gapness consistently from the realized chunk times in solver.py the same way get_detailed_solution already does, so the UID and the stored metric agree. At minimum, document that metrics.min_time/gapness are advisory and undefined under tmax.
- **[medium]** Under-sampled 'abandoned' cells bypass the CV noise gate and inflate baselines/speedups _(verify: confirmed)_  
  The calibrated sampler records abandoned cells with a single sample (count=1), which makes timing.cv trivially 0.0 (no variance with one point). profiling_loader only filters on throttled + cv<=max_cv (profiling_loader.py:90-93) and never inspects provenance.abandoned, so a single-sample 465ms measurement passes the noise gate precisely because it is under-sampled. These values flow unweighted-by-confidence into both the z3 cost matrix and the baseline column sums (baselines.py:47-53). For the z3 matrix a large value is harmless (never picked), but for the OMP/GPU baseline sum it directly inflates baseline_data and therefore every speedup_over_cpu/gpu reported in the schedule JSON.  
  _evidence:_ bm_prof_common.hpp:95-98 (abandoned -> out.assign(1,c)); cv computed as 0 for single sample at bm_prof_common.hpp:222; profiling_loader.py:90-93 filters only throttled+cv; confirmed real abandoned cells e.g. R5CY21Y3VEV/cifar-sparse/vulkan stage1 big p50=465.9 cv=0.0 count=1  
  _fix:_ Have the loader treat provenance.abandoned (and/or timing.count below a floor) as a confidence signal: exclude such cells from baseline column sums, or surface them in the report and require they be excluded for speedup reporting. The CV gate alone cannot detect single-sample noise.
- **[low]** smt/README.md documents a stale solve_optimization_problem / baseline API _(verify: confirmed)_  
  smt/README.md shows solve_optimization_problem(stage_timings, baseline_data, num_solutions, app) and passes baseline_data into the solver, but the actual signature is solve_optimization_problem(stage_timings, num_solutions=30, app_name=None, minimize_mode='gapness', gpu_backend=None) and the solver no longer takes baseline_data at all (baselines are merged in later by dump_solutions_as_json). A reader following the README would write code that fails. The README is the documented entry point for the package.  
  _evidence:_ optimizer/smt/README.md:64-76 vs solver.py:22-28 (no baseline_data param) and solution_analyzer.py:228 (baseline merged at dump time)  
  _fix:_ Update the smt/README usage block to the current signature (drop baseline_data from the solve call; show minimize_mode/gpu_backend) so it matches solver.py and 02_gen_schedule_merged.py.
- **[low]** 04_parse_schedules.py hard-couples to the optional matplotlib/plot extra at import time _(verify: confirmed)_  
  04_parse_schedules.py imports create_comparison_visualization at module top (line 31), and analysis/results/visualization.py imports matplotlib/numpy unconditionally at its top (lines 12-13). matplotlib is only in pyproject's optional 'plot' extra, not core deps. So running the parser without the plot extra installed fails with ImportError before any work, even though the script explicitly supports a no-visualization path (only calls create_comparison_visualization when --output is given).  
  _evidence:_ optimizer/orchestrate/04_parse_schedules.py:31; optimizer/analysis/results/visualization.py:12-13; optimizer/pyproject.toml (matplotlib/pandas only under [project.optional-dependencies].plot)  
  _fix:_ Make the visualization import lazy (import create_comparison_visualization inside the `if args.output:` branch), or move matplotlib to core deps. Lazy import keeps the analysis/parse path runnable with only core deps.
- **[low]** Baseline-selection logic (test_baselines.py) is not exercised by CI _(verify: confirmed)_  
  test_baselines.py validates the load-bearing baseline logic (GPU=backend column sum, OMP=fastest fully-measured CPU tier, absent->None, Big-only minipc vs all-tier phone selection) but its functions are check()/main(), not test_*, and it reads the un-versioned data/profiling store. CI runs `uv run pytest -q` (ci.yml:80) which collects only the 14 test_* functions; test_baselines is silently skipped, and the store it needs would not exist in CI anyway. So a regression in baselines.py tier-selection or the column_sum 'all stages measured' guard would not be caught by CI.  
  _evidence:_ ci.yml:68-80 (`uv run pytest -q`, testpaths=tests); pytest --collect-only shows 14 tests, none from test_baselines.py; test_baselines.py:45,71 define check()/main(); STORE=data/profiling (gitignored per .gitignore:52)  
  _fix:_ Add a small committed JSONL fixture (a few stages x tiers, like tests/fixtures) and a pytest-collected test_* that drives get_baseline_for_config against it, so the tier-selection logic is gated in CI without depending on the regenerable store.
- **[low]** Solver has no defensive check that len(stage_timings) matches the app's stage count _(verify: confirmed)_  
  define_data derives num_stages from app_name independently of the passed stage_timings (data_loader.py:75-83); if they disagree the solver indexes stage_timings[k] out of range and raises a bare IndexError rather than a clear validation error. The sole production caller (02) always builds both from the same app so they match, but the contract is implicit and the failure mode is opaque.  
  _evidence:_ data_loader.py:78 (num_stages from app); constraints.py:63 indexes stage_timings[k]; reproduced: solve_optimization_problem(5-stage timings, app='tree'/7) -> IndexError: list index out of range  
  _fix:_ Add `assert len(stage_timings) == num_stages` (or a ValueError with a clear message) at the top of solve_optimization_problem/define_data so a profiling/app-stage mismatch fails with an actionable message instead of a raw IndexError.

**Verifier flagged as missed:**
- Production-path CV gate is effectively a near-no-op: both data_loader.load_stage_timings (data_loader.py:19) and baselines.get_baseline_for_config (baselines.py:39) pass max_cv=1.0 (CV up to 100%), whereas profiling_loader's own default and CLI default is max_cv=0.1 (profiling_loader.py:67,124). So the strength 'drops throttled/high-CV samples' is true of the function but, at the values the real pipeline calls it with, only the explicit thermal-throttle flag does meaningful filtering. This both weakens strength #2 and amplifies finding #2 (single-sample abandoned noise sails through with room to spare).
- UID instability across modes was demonstrated but not called out by the eval: the SAME schedule SCH-G3B4-...-4291 appears in BOTH the tmax and gapness outputs of minipc/tree/vk but with different reported metrics.gapness (0.7371 in tmax vs 0.0213 in gapness). The UID is chunk-derived and stable; the stored metric is not. Anyone diffing the two schedule files would see an identical assignment labeled with contradictory gapness, which is a concrete downstream-confusion consequence of finding #1.
- abandoned cells are NOT entirely harmless to the z3 cost matrix on single-tier devices: the eval says a large abandoned value is 'harmless (never picked)' for z3, but on the Big-only minipc (and any device where the only present CPU tier has an abandoned stage), the inflated value is the ONLY CPU option, so it does enter the assignment trade-off against GPU rather than being dominated away. The 'never picked' reasoning assumes a cheaper alternative tier exists.
- Cross-run percentile aggregation is acknowledged-but-statistically-unsound and the eval did not flag it as a correctness caveat: profiling_loader.py:100-101 count-weights p50/p95 across runs, which the module docstring (lines 14-17) itself admits is 'a count-weighted point estimate, not a true pooled percentile.' For p95/p99 in particular this can materially misstate the tail that feeds baselines/speedups.
- speedup_over_gpu's gpu_key heuristic (solution_analyzer.py:253-256) picks 'the first baseline key not in [omp, fastest]' rather than the actual requested backend token; it works today only because baseline_data carries exactly one extra key (vk or cu), an implicit single-extra-key assumption similar in spirit to finding #6.
