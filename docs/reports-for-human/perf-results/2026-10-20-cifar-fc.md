# cifar Vulkan FC: clustered reduction, once-per-batch layouts, INT8 weights (2026-10-20)

**Change:** OpenSpec `cifar-gpu-kernels`, task group 3 (commits 87ea378 to the task 3.10 commit on
`feat/cifar-fc-weights`; the last code commit is 258b3c5) · **Targets:** Pixel 7a (Mali-G710, subgroup 16), Samsung
Galaxy (Xclipse 940, subgroup 64) · **Tool:** `bm-prof-cifar-{dense,sparse}-vk`, per-stage GPU timestamps, with the GPU
clock it records · rocky-ryzen ran correctness tests only, no timing.

> **One-line finding:** in the default FP32 mode cifar-sparse fc1 + fc2 take 37.3 instead of 54.1 ms on the Pixel
> (-31 %) and 18.7 instead of 20.1 ms on the Samsung (-7 %), from a subgroup reduction that took the accumulators off
> Mali's stack. Opt-in INT8 weights (`BT_VK_FC_WEIGHTS=int8`) cut cifar-dense fc1 / fc2 to 0.66 / 0.45 of FP32 on
> the Pixel and 0.60 / 0.60 on the Samsung at unchanged accuracy on the 128 exported test images. Layouts that load
> each weight in one workgroup were 21-337 % slower; FP16 weights were not faster on the Samsung and were removed.

## What changed

- **F3, clustered reduction.** `new_cifar_dense_linear_bt.comp` (both apps' fc1-fc3) sums each row's 16 lane
  partials with `subgroupClusteredAdd(…, 16)` (the pipeline is subgroup-size dependent, so rows are aligned
  clusters). A device without clustered operations (`ComputeLimits::subgroup_clustered`, new) gets
  `new_cifar_dense_linear_bt_portable.comp` instead, the same body (`new_cifar_dense_linear_bt.glsl`) with the
  shared-memory reduction and no subgroup capability in its SPIR-V. On Mali the old reduction indexed the
  accumulators with a loop variable, which put both arrays on the stack (malioc: alloca 128 B, spill 80 B, LS 59.2
  cycles); clustered there is no alloca (LS 28.8).
- **F1, weights once per batch: no new layout.** Three layouts in which one workgroup covers the whole batch,
  (a) K outer / tiles inner, (b) batch split, (c) lanes split tiles x K halves, were all slower than linear_bt. Its
  launch-order remap already puts the 8 batch-tile workgroups of a row-group next to each other, so they read each
  weight slice from DRAM once through L2: without the remap the Samsung's fc1 / fc2 take 29 % longer. Kept as is.
- **F2, INT8 weights, opt-in.** `BT_VK_FC_WEIGHTS=int8`: the AppData quantizes fc1 and fc2 once at construction
  (`platform/util/fc_weights.hpp`, per output row `scale = max|w| / 127`, `|w - scale q| <= scale / 2`); linear_bt
  (`WEIGHTS`, spec constant 2) reads the bytes as 32-bit words through an aliased binding, sign-extends them and
  applies the scale to the row's sum. No optional device feature is needed. On subgroups of 32 and more INT8 rows own
  4 output features (`FPR`, spec constant 3): at 2 the Samsung's INT8 was bound by the shared-memory input reads.
  fc3 and every FP32 pipeline keep 2. The default (unset) mode makes no copy and runs the FP32 code.
- **FP16 weights:** built, correct, accuracy unchanged, 31 % faster on the Pixel, removed: on the Samsung they ran at
  450 MHz in 2.3 ms while FP32 alternates between 2.0 ms (800 MHz) and 2.9 ms, so not faster beyond noise (the
  phone gate is binding).
- **Tests added:** `LinearBt.*` (ragged shape, both modules, INT8 at FPR 2 and 4, against the weights as the
  kernel decodes them; the portable module's SPIR-V has no subgroup capability), `FcWeights.QuantizeRoundTripWithinBound` (`ctest -L omp`), `Cifar{Dense,Sparse}Vk.
  RealWeights_EndTaskAccuracy` (FP32 vs INT8 over the 128 exported images), an optional per-stage tolerance hook
  for the diff oracles (INT8 fc1/fc2: rtol 2e-2, atol 1.5e-2; end to end 2e-2 / 2e-2).

The Samsung always ran FP16 at 450 MHz: 1.03 M GPU cycles against FP32's 1.6-1.8 M, but FP32 alternates between
2.0 ms at 800 MHz and 2.9 ms at 500-650, so FP16 is faster than some FP32 runs and slower than others. INT8 (1.72 ms
at 400-450 MHz) is below every FP32 run.

## Findings and caveats

- **cifar-dense FP32 on the Pixel is not faster, and its medians are higher (fc1 +8 %, fc2 +34 % here; fc1+fc2
  +8 % in the 3.2 session).** The dense FC follows the governor: the before kernel took ~3.15 M GPU cycles at every
  clock (6.85 ms at 471 MHz, 4.95 at 633, 4.23 at 762), the after kernel matches it at 471-510 MHz (3.1-3.5 M) but
  needs 4.2 M at 633 MHz, about 6.6 ms whatever the clock above 471. So above 471 MHz it waits on memory, and the
  before kernel's stack spills (gone with F3) may have kept the memory clock up; that is a guess: the profiler
  records the GPU clock only. No group-3 gate covers cifar-dense FP32; it is recorded here as a regression to look at.
- The Samsung's GPU clock settles lower when a kernel needs fewer cycles (as in group 2), which is why FP16 lost and
  why INT8 needed 4 features per row to win in wall time.
- **Accuracy** is measured on the 128 exported test images (the full test set is not exported): FP32 and INT8 both
  classify 118/128 (cifar-dense, 92.19 %) and 120/128 (cifar-sparse, 93.75 %) on every device. One image is 0.78
  points, so "within 0.5 points" means the same count.
- **Profiling data:** cifar x VK fc stage times changed; regenerate the profiling stores and schedules before
  reporting new fleet results (and profile INT8 separately if a schedule should use it).
